Why this matters for Garanti

Before mesh (app framework)

  • gRPC client keeps long-lived connections
  • Many RPCs stick to same backend pod
  • Keepalive / idle timeout in app config

After mesh (Istio sidecar)

  • Envoy load-balances each RPC (HTTP/2)
  • Connection pool owned by DestinationRule
  • Remove duplicate app + proxy settings

The key insight: two separate TCP connections

Conn A Client reuses channel to sidecar  ·  Conn B Proxy owns upstream TCP — DestinationRule

Inside the sidecar — where TCP & pools are established

Conn A not in DestinationRule  ·  Conn B + pools = trafficPolicy.connectionPool on grpc-echo host

Two different questions — don't mix them up

Per-RPC load balancing

Which pod handles this RPC?

  • Envoy L7 LB — always for gRPC in mesh
  • ROUND_ROBIN in DR
  • Visible in PromQL / quoted pod IP in logs
  • Does not require new TCP per RPC

Per-RPC TCP (churn)

New upstream socket for this RPC?

  • Only when DR forces recycle
  • maxRequestsPerConnection: 1
  • idleTimeout + gap between RPCs
  • Visible in observe-tcp.sh

1 client TCP, 10 gRPC messages — how many upstream TCPs?

Scenario Upstream TCP count Pod spread
Baseline (maxReq=0, no short idle) ~1–3 reused Can hit all 3 pods
maxRequestsPerConnection: 1 ~10 (one per RPC) Can still hit all 3 pods
idleTimeout: 5s, gap 10s between RPCs ~10 (one per RPC) Can still hit all 3 pods
10 RPCs in 1 second, baseline few reused Spread across pods

Yes, theoretically 10 upstream TCPs from 1 client connection — but only when pool policy + timing demand it, not by default.

Lab Step 2 — maxRequestsPerConnection (fast client)

WITHOUT (baseline)

5 qps · 30s window · maxReq: 0

~6 unique ports · REUSE

Many RPCs share few upstream TCP sockets

WITH maxReq: 1

Same client · apply manifest 05

~150 unique ports · CHURN

Envoy closes upstream TCP after every RPC

Lab Step 3 — idleTimeout (slow client)

Slow client: 1 RPC / 10s · -c 1 (one client channel) · gap > idleTimeout: 5s

Why define idleTimeout? Central mesh policy · cap stale upstream sockets · align with firewall/NAT timeouts · migrate from app framework.

Lab Step 4 — tcpKeepalive vs idleTimeout

Step 4: tcpKeepalive, no short idle

~1–3 ports · REUSE (like Step 3a)

Step 3b: idleTimeout: 5s

~9 ports · CHURN

Keepalive keeps the TCP wire healthy through idle gaps. It does not prevent HTTP/2 idle close.

Reading access logs (grpc-client → istio-proxy)

... "10.128.0.85:8079" ... outbound|8079||grpc-echo... 10.128.0.11:57116 ...

  • Quoted IP "10.128.0.85:8079" → which echo pod (LB)
  • Port after outbound| :57116 → Envoy→pod TCP (Conn B)
  • Same port twice = REUSE
  • All different = CHURN

Risk: duplicate app + Envoy settings → RST, UNAVAILABLE, flaky streams. One owner per knob.

Not in DR: ingress 2 MB body limit (gateway config) · proxy :15021 readiness vs app liveness.

Summary — three sentences for the room

  1. The mesh load-balances each gRPC RPC — you don't need connection churn for spread.
  2. The client owns Conn A to the sidecar; DestinationRule owns Conn B to pods — independent.
  3. idleTimeout and maxRequestsPerConnection control when Envoy recycles upstream TCP — visible with observe-tcp.sh.
